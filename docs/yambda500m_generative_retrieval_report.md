# Generative Retrieval с Semantic ID на Yambda-500M: сравнение токенайзеров и TIGER против SASRec

**Аннотация.** Мы переносим парадигму TIGER — sequential recommendation через генерацию дискретных Semantic ID — на музыкальный датасет Yambda-500M с корпусом порядка 480 тыс. треков и ~110 млн прослушиваний. Сравниваем три способа построения Semantic ID (RQ-VAE, RQ-KMeans, RQ-OPQ) при фиксированном encoder-decoder decoder и оцениваем качество против SASRec на time-based split с маскированием train-истории (filter_seen). Лучший токенайзер — RQ-OPQ: +7% recall@10 относительно RQ-VAE при существенном снижении коллизий. Тем не менее generative retrieval уступает SASRec (recall@10: 0.023 vs 0.026). Без filter_seen метрики TIGER завышаются в ~6 раз. На масштабе Yambda-500M Semantic ID требует обязательной dedup-колонки и тщательного выбора квантизатора; «голый» TIGER не даёт выигрыша над классическим sequential baseline.

**Ключевые слова:** generative retrieval, semantic ID, RQ-VAE, RQ-OPQ, TIGER, SASRec, Yambda, sequential recommendation

---

## 1. Введение

TIGER (Rajput et al., NeurIPS 2023) предлагает заменить скоринговый retrieval генерацией Semantic ID — иерархической последовательности дискретных токенов, полученных квантизацией контентных эмбеддингов айтема. Encoder-decoder обучается предсказывать следующий Semantic ID в пользовательской последовательности; сгенерированный ID сопоставляется с треком в каталоге.

Оригинальные эксперименты TIGER ограничены категориями Amazon Reviews (десятки тысяч айтемов). Мы проверяем, сохраняется ли преимущество подхода на **крупном музыкальном каталоге** с готовыми audio-эмбеддингами и сотнями тысяч треков. Бейзлайн — **SASRec**, стандартная self-attentive sequential модель без промежуточной дискретизации.

---

## 2. Датасет

**Yambda-500M** (Yandex, HuggingFace) — срез из 500 млн взаимодействий платформы музыкального стриминга: прослушивания (listens), лайки, дизлайки, временные метки, флаг organic/recommendation-driven, precomputed audio embeddings для 7.7 млн треков.

Для экспериментов подготовлен поднабор **listens_fltrd**:

- **Тип событий:** прослушивания треков (implicit feedback).
- **Фильтрация flat-лога:** `timestamp > 18 000 000` (отсечение раннего «хвоста» датасета, где timestamp начинается с 0) и **played_ratio_pct > 90%** — оставляем фактически полные прослушивания, отсекая случайные скроллы и отказы.
- **Итоговый объём:** ~**103–110 млн** событий, ~**1.2 млн** уникальных item_id в логе, **478 583** трека с доступными audio embeddings в корпусе токенайзера.
- **Пользователи:** ~90 тыс. в train, ~45 тыс. в eval (после temporal split и пересечения с test).

**Протокол разбиения:** time-based split по стандартным константам Yambda (TEST_TIMESTAMP = 25 960 000, gap 30 мин). Модель предсказывает будущие прослушивания по прошлым — не leave-one-out.

**Протокол оценки filter_seen:** перед подсчётом recall/NDCG из рекомендаций исключаются все треки, которые пользователь уже слушал в train. Без этой маски generative retrieval систематически «рекомендует» айтемы из истории, завышая метрики.

---

## 3. Метод

### 3.1. Pipeline

Каждый трек кодируется в последовательность Semantic ID: несколько слоёв квантизации контентного эмбеддинга (128-мерный normalized audio embedding) плюс **dedup-колонка** — порядковый индекс внутри группы айтемов с одинаковым semantic prefix (стандарт TIGER). Замороженный токенайзер преобразует пользовательские последовательности в цепочки токенов; encoder-decoder (T5-подобная архитектура, 2 слоя, d=128) обучается предсказывать следующий Semantic ID. На инференсе — beam search по semantic tokens (K=50) и lookup в таблице semantic-ID → item.

### 3.2. Токенайзеры

| Токенайзер | Структура ID | Обучение |
|------------|--------------|----------|
| RQ-VAE | 3 RQ-слоя + dedup (4 токена) | reconstruction + VQ |
| RQ-KMeans | 3 RQ-слоя + dedup | residual k-means |
| RQ-OPQ | 3 RQ + 2 OPQ subspace + dedup (6 токенов) | RQ-KMeans + product quantization |

Все токенайзеры: codebook size 128, latent dim 32. Decoder для каждого варианта обучен 25 000 итераций при прочих равных.

### 3.3. Бейзлайн

**SASRec** — item-ID sequential model, обученная на тех же последовательностях. Дополнительно: popularity baseline (лучший час дня).

---

## 4. Эксперименты

1. Воспроизведение TIGER с RQ-VAE и dedup на полном корпусе.
2. Сравнение токенайзеров RQ-KMeans и RQ-OPQ при том же decoder.
3. Диагностика влияния dedup-колонки и протокола filter_seen.
4. Сравнение с SASRec и popularity на едином eval-протоколе.
5. Три стратегии снижения коллизий поверх лучшего токенайзера (RQ-OPQ): HaMR, popularity-ordered dedup, RRS.

---

## 5. Результаты

### 5.1. Качество рекомендаций (filter_seen)

| Модель | Recall@10 | NDCG@10 | Recall@50 | NDCG@50 |
|--------|-----------|---------|-----------|---------|
| **SASRec** | **0.0258** | **0.1640** | **0.0401** | **0.3811** |
| RQ-OPQ + TIGER | 0.0226 | 0.1503 | 0.0265 | 0.3054 |
| RQ-KMeans + TIGER | 0.0211 | 0.1417 | 0.0225 | 0.2793 |
| RQ-VAE + TIGER | 0.0211 | 0.1406 | 0.0201 | 0.2554 |
| Popularity | 0.0260 | 0.1498 | 0.0361 | 0.3060 |

RQ-OPQ — однозначный лидер среди токенайзеров (+7% Recall@10 к RQ-VAE). RQ-KMeans не превосходит RQ-VAE по ranking-метрикам. **SASRec остаётся сильнее** generative retrieval по Recall@10 и NDCG@10. Popularity конкурентен по Recall@10, но проигрывает по NDCG@50 — персонализация TIGER/OPQ работает на длинных списках.

### 5.2. Коллизии Semantic ID

| Токенайзер | Доля уникальных full-ID | max_dedup | Доля айтемов в colliding triplets |
|------------|-------------------------|-----------|-----------------------------------|
| RQ-VAE | — | 1 123 | — |
| RQ-KMeans | 37.4% | 1 140 | 78.1% |
| **RQ-OPQ** | **90.0%** | **468** | 78.7% |

На 478K треков RQ-OPQ радикально снижает нагрузку на dedup: 90% айтемов получают уникальный 5-token prefix без счётчика коллизии. У RQ-KMeans почти 2/3 айтемов различаются только dedup-токеном — последний слой ID по сути не семантический.

### 5.3. Борьба с коллизиями

На каталоге 478K треков коллизии semantic prefix неизбежны: без dedup-колонки lookup неинъективен, с ней — часть токенов перестаёт быть семантической. Поверх RQ-OPQ (лучший токенайзер) проверили три подхода из недавней литературы.

**HaMR** (QuaSID) — вспомогательный loss при обучении квантизатора, который штрафует близкие эмбеддинги за попадание в один prefix. Доля уникальных full-ID выросла с 90.0% до **93.4%**, но max_dedup — с 468 до **2371**: коллизии «размазались» по большему числу dedup-слотов. На инференсе — **8944 lookup miss** против нуля у baseline. Downstream: recall@10 **0.0214**, ndcg@10 **0.143** — хуже sequential OPQ.

**Popularity-ordered dedup** — внутри группы colliding prefix айтемы нумеруются по убыванию популярности (число прослушиваний в логе). Гипотеза: частые треки получают «канонический» dedup=0, редкие — смещённые индексы. Результат: recall@10 **0.0195**, ndcg@10 **0.135** — ниже baseline; перестановка dedup-счётчиков без изменения prefix не даёт прироста.

**RRS** (Purely Semantic Indexing) — при построении корпусной таблицы ID каждый трек получает ближайший свободный semantic prefix (greedy nearest neighbor + DFS backtracking, top-k=4). **89.3%** айтемов индексируются без коллизий, dedup_vocab сжимается до **1** — dedup-колонка фактически не нужна. Downstream: recall@10 **0.0220**, ndcg@10 **0.146** — на уровне baseline, с небольшим отставанием по recall и **1188 lookup miss**.

| Стратегия | full-ID unique | max_dedup | Lookup miss | Recall@10 | NDCG@10 |
|-----------|----------------|-----------|-------------|-----------|---------|
| OPQ + sequential (baseline) | 90.0% | 468 | 0 | **0.0226** | **0.150** |
| OPQ + HaMR | 93.4% | 2371 | 8944 | 0.0214 | 0.143 |
| OPQ + popularity dedup | 90.0% | 470 | 1205 | 0.0195 | 0.135 |
| OPQ + RRS | 89.3%* | 1 | 1188 | 0.0220 | 0.146 |

\*доля айтемов, получивших уникальный prefix через nearest-neighbor индексацию.

Ни одна стратегия не превзошла простой sequential assignment поверх RQ-OPQ. Улучшение collision-статистик на этапе токенайзера (HaMR) или почти полное устранение dedup (RRS) не конвертируется в лучшие рекомендации. Борьба с коллизиями на Yambda-500M — отдельная инженерная ось, ортогональная качеству decoder-а.

### 5.4. Dedup-колонка обязательна

| Конфигурация | Recall@10 | NDCG@10 |
|--------------|-----------|---------|
| TIGER без dedup | 0.015 | 0.102 |
| TIGER с dedup | 0.021 | 0.141 |

Без dedup lookup неинъективен: массовые коллизии prefix-а ломают однозначное соответствие ID → трек. Потеря ~30% Recall@10.

### 5.5. filter_seen: без маски метрики нерепрезентативны

| Модель | Recall@10 | NDCG@10 | | Recall@10 | NDCG@10 |
|--------|-----------|---------|---|-----------|---------|
| | **без filter_seen** | | | **с filter_seen** | |
| TIGER + dedup | 0.129 | 0.422 | → | 0.021 | 0.141 |
| SASRec | 0.065 | 0.325 | → | 0.026 | 0.164 |

Generative retrieval особенно уязвим: модель воспроизводит Semantic ID из train-истории, и без маскирования Recall@10 завышается **в 6 раз**. Для SASRec завышение умереннее (×2.5), но тоже существенно. Любое сравнение TIGER с дискриминативными моделями на sequential данных **требует filter_seen**.

## 6. Обсуждение

**Semantic ID на промышленном масштабе — не plug-and-play.** RQ-VAE из коробки, RQ-KMeans и даже улучшенный RQ-OPQ требуют цепочки инженерных решений: dedup-колонка, диагностика коллизий, выбор числа иерархий, корректный eval-протокол. Универсального рецепта «обучил квантизатор — получил retrieval» нет: каждый токенайзер несёт компромисс между уникальностью ID, семантической осмысленностью токенов и сложностью decoder-а.

**TIGER в нашем сетапе не дал выигрыша.** При честной оценке RQ-OPQ + TIGER уступает SASRec, хотя токенайзер существенно лучше исходного RQ-VAE. Это не опровергает идею generative retrieval в целом — наша реализация decoder-а (25k итераций, frozen tokenizer, audio-only semantics) может быть далека от потолка. Тем не менее факт остаётся: **на Yambda-500M классический sequential baseline выигрывает без дополнительной дискретизации и без борьбы с коллизиями.**

**С SASRec «танцев с бубном» не требуется.** Один этап обучения, нативные item ID, стандартный eval — и результат выше. Generative retrieval оправдан только если дискретные ID дают измеримый прирост, которого мы на текущем этапе не наблюдаем.

Открытый вопрос — можно ли закрыть разрыв с SASRec улучшением токенайзера (снижение коллизий без non-semantic dedup), обучением end-to-end или введением collaborative signal в Semantic ID. Это отдельная линия работы; настоящий отчёт фиксирует baseline, на котором такие гипотезы должны проверяться.

---

## 7. Заключение

На Yambda-500M (~110 млн полных прослушиваний, 478K треков в корпусе) мы воспроизвели TIGER, сравнили три токенайзера Semantic ID и показали, что **RQ-OPQ** существенно лучше RQ-VAE и RQ-KMeans по коллизиям и downstream-метрикам. Три стратегии борьбы с коллизиями (HaMR, popularity dedup, RRS) не превзошли baseline OPQ. **SASRec остаётся сильнее** при корректном протоколе filter_seen. Критичны: dedup-колонка на большом каталоге, диагностика коллизий и маскирование train-истории при оценке. Generative retrieval через Semantic ID на музыкальном large-scale датасете пока не конкурентен классическому sequential подходу.
